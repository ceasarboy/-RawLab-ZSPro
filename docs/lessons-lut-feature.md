# 经验教训：LUT 库功能开发全过程复盘

> 范围：2026-10-03 一天内完成的"松下式 LUT 载入 + 双 LUT 组合器 + STD 底座适配"功能族的
> 开发-真机调试循环。沉淀给后续所有功能开发（裁切、四面体插值、fit-lut）复用。

## 一、流程教训（最重要的三条）

### 1. 数值代码必须"宿主逐点验证 → 再上真机"

红屏事故（STD 适配牛顿符号写反）的根本原因不是数学——数学在 Python 里验证过——
而是 **C++ 移植后从未在宿主上做过数值验证**，直接进了真机。宿主上写一个 20 行的
dump 工具（adapt_check.cpp）五分钟就定位了"适配输出与输入无关、卡死在角点"。

**纪律**：任何数值/算法代码，合并前必须在宿主 harness 中有数值锚点用例
（端点值 + 单调性 + 已知映射的抽样对比）。"编译通过 + 单元测试绿"不等于数值正确。

### 2. 真机报告是定位线索，宿主复现是定位手段

三轮真机反馈（"处理失败+predicate 异常"、"满屏红"、"无法切换"）各自指向不同 bug，
但每一轮的定位都是靠：用户提供的关键字/截图 → 宿主复现或静态锁定 → 修复 → 再验证。
用户的错误消息原文（"collection contains no element matching the predicate"）
一次就锁定了 Kotlin 层 bug。**引导用户报告原始错误文本和截图，是最高效的调试输入。**

### 3. 同文件多轮 patch 必须基于最新状态

crop 回退覆盖了刚写入的 B 槽签名；B 槽 patch 的 old 串又基于过时内容 assert 失败；
参数顺序在头文件与实现间漂移。教训：
- 改代码用 Read + Edit（精确锚点），不用"长 heredoc + 多段 replace"；
  长 heredoc 还会因 `\n`/`\"` 转义损坏 C++/Java 字符串字面量（本次发生了 4 次）；
- 每轮功能完成即构建 + 提交（本地 commit），不把多个功能叠在未验证的工作区里。

## 二、技术教训

### 4. Kotlin companion object 里的 external 函数 JNI 符号在 Companion 类上

`companion object { external fun foo() }` 生成的 JNI 符号是
`Java_..._NativeProcessor_Companion_foo`，与 C++ 侧 `Java_..._NativeProcessor_foo`
不匹配 → 调用时 UnsatisfiedLinkError → 被 `catch (Throwable)` 吞掉 → 静默失败。
**新 JNI 函数一律声明为类实例方法**（与已验证正常的旧函数同形态）；
`catch (Throwable)` 的静默吞异常必须有日志或用户可见反馈，不能无声。

### 5. 静默失败是 UX 毒药

"无法切换"实为三层静默：适配失败被吞 + 进度不可见 + 完成消息被对话框遮挡。
修复模式：异步操作期间对话框内进度条、完成/失败后**对话框自动关闭**让 snackbar
可见、失败给专属文案（不复用无关错误消息）。通用原则：**每个异步操作必须有
用户可见的进行中/成功/失败三态**。

### 6. 数值迭代的边界与初值

- 牛顿迭代符号写反（+ 而非 −）→ 正反馈发散到立方体角点（红屏/全白）；
- 初值/seed 链在边界附近会传染卡死（J 奇异 break 后 seed 传染后续所有点）；
- 有限差分在 clamp 边界处列归零 → det=0。
**修复组合**：每点独立求解（去 seed 链）+ 正向牛顿 + 收敛校验 + 失败点暴力
最近邻回退。全部配了 harness 用例（端点保持、中性轴单调）。

### 7. "标注不可靠，手工兜底"——数据驱动的功能必须有手动覆盖

RedNose 的文件是 STD 底座但无 `#LUMIXPHOTOSTYLE STD` 标注 → 自动嗅探必然漏。
结论：自动识别只做便利默认，**用户手动切换（底座 chips + 可逆的原始文件保留）
是功能主路径**。数据格式的机器可读标注（富士的 `#Gamma/#Gamut` 头是正面样板）
应写入解析器并在文档中鼓励。

### 8. 验证资产要沉淀成可重复运行的工具

本次沉淀、后续直接复用：
- `host-harness/lut_mode_harness.cpp`（33 项：三模式契约/恒等零差异/双后端
  对拍/栈槽/烘焙/适配端点与单调）
- `host-harness/adapt_check.cpp`（适配数值锚点 + 对角线 dump）
- `verify_log_curves.py`（log 解码锚点，colour-science 对拍）
- `make_test_luts.py` / `make_look_library.py`（测试与起步风格生成器，含自检）
- `haldclut_to_cube.py`（HaldCLUT 生态转换，恒等端到端校验）

- APK 内：官方 STD→V-Log 映射表（松下版权，仅取 functionality，个人使用）+
  富士官方 F-Log2 LUT（随 App 授权）+ 自产风格（MIT 无限制）

## 四、补充（2026-10-04 深夜）：STD 适配断层与穷举验证

### 8. "抽样验证"与"穷举验证"是两种 guarantee

红屏修完、宿主 33 项"全绿"之后，真机仍然出现色彩断层——因为 33 项里对适配器的
检查是**抽样**（对角线 9 点、轴 9 点、4 个灰阶），而断层发生在**格点相邻关系**
和**特定色相象限**里，抽样根本踩不到。用户一句"灰阶你测了几个值？256 级全测过吗"
直接戳穿。

**纪律**：颜色管线验证的最低标准是——

- R/G/B/gray 四条 ramp × 256 级**全量**（单调、平滑、灰保持、端点）；
- 全格点 6-邻域跳变普查（任何 look/适配产物）；
- 饱和度阶梯（同 hue 多档 chroma，测 gamut 投影平滑性）；
- ColorChecker 全 24 色块或等效覆盖（紫/品红象限不能缺席）。

`ramp_check.cpp` 已按此实现：修正前它甚至抓出了"检查语义本身"的问题
（把 look 的合法交叉通道特征计成违规；把不同 ramp 的差异当成失败）。
检查器和被检代码一样需要被审。

### 9. 用受控实验分离变量，而不是在真机上迭代猜

四臂噪声实验（中性/直套/官方分层/逆适配，256 次噪声实现 × 4 灰度）一次把
"彩噪来自哪一层"定死：逆适配 LUT 色度 σ 2.27–3.04，官方分层链 0.77–1.22，
中性 0.80。数据指认逆适配格点噪声后，方案选择（分层链替代 3D 逆）就不需要
争论。**先建四臂定量实验，让数据指认根因，再改代码。**

### 10. 研究先行救了一次大返工

用户叫停"继续调 Newton"并要求先分析松下 App。Lumix Lab APK 逆向（JADX +
native 符号 + 资产分类）确认：手动导入路径没有底座逆变换；`STD_to_VLOG` 是
自动估计链的技术 transform；白墙黑白噪声与松下 native pipeline 的
noise_L/noise_C/cromaNrLevel 分层一致。若继续在逆适配上投入，方向本身就是错的。

### 11. 分层架构是可扩展的正解

STD 底座适配的最终形态不是"一张修正 LUT"，而是：

```text
中性显示值 -> 场景线性 (neutralDecode)
          -> STD 显示曲线 (官方映射灰轴反演, 1D)
          -> look LUT (其声明底座域)
```

1D 曲线严格灰保持（R=G=B 逐点成立）→ 适配本身对中性内容零色度噪声。
换其它底座（CNEV2/NAT）= 换一条 1D 曲线。组合器、叠加强度、未来裁切
全部架在这个分层上，互不污染。

### 12. 数值噪声度量必须分"亮度/色度"两条，且用 patch-mean 而非基准值

第一版 noise_check 的亮度指标拿渲染值减"输入基准值"——把 tone 曲线整体位移
误报成噪声（σ 36-65 的荒谬值）。正确度量：亮度噪声 = 像素均值对 patch 均值的
偏差；色度噪声 = 三通道对像素自身均值的偏差。**度量定义错了，实验结论就是错的。**

## 五、补充（2026-10-04）：四面体插值替换三线性

### 13. 插值器换血后，绝对阈值检查必然失效——阈值必须锚定源数据

三线性对非单调源数据有"顺手抹平"效应；四面体忠实呈现数据。换插值器后
ramp_check 开始报 gray ramp 非单调——追查发现是 adapted cube 暗部格点
**本身**就有 -3.3e-4 的对角 dip（Newton 适配的固有特性），三线性一直在
掩盖它。诚实口径是"插值不得引入源数据没有的行为"：

- 单调性：孤立反向（连续 <3 级、降幅 >1e-4）才算违规；连续 >=3 级同向
  下降是 look 的合法压暗段（Velvia 高饱和区陡降实测 -0.08/格点）；
- 灰保持阈 = max(0.02, 1.5 × 源灰对角通道偏差)；
- 跳变普查阈 = max(0.12, 1.2 × 源轴边最大跳变)。

改完后四个 adapted 产物全 PASS，且每张 LUT 的输出灰偏差与源对角偏差
**逐位相等**（0.0042=0.0042 等）——这才是"插值正确"的可证伪判据。

### 14. 检查器自身会越界放水

ramp_check 的自通道单调检查写 `o[c]`，gray ramp 的 c=3 直接越界读堆垃圾，
垃圾值"恰好单调"，连续几轮验证静默通过。**检查器与被检代码适用同样的审查
标准**——越界读不崩不代表没越界，sanitize 一遍检查器里的所有下标来源。

### 15. 四面体的取舍要如实记录

- 收益：4 次采样替代 8 次；饱和区色相不随通道漂移（OCIO/Resolve/FFmpeg
  的标准做法）；格点处输出与源数据严格一致。
- 代价：a=b=c（格胞中心）时权重全落在主对角两端 000/111，中间角点权重为 0
  ——对非对角单调的合成函数，中心误差可以比三线性大。真实 film look 数据
  近似对角单调，是净收益；不要拿合成函数 A/B 后宣称"全面更准"。
- 纪律：GLES / D3D11 / Metal / CPU 四条路径必须同一提交内同步替换，否则
  gpu_photo_tests 的 CPU/GPU 对比（max DN 0）立即失配暴露。

### 16. 检查脚本的"恒等"语义与量纲——被巨大的假失败逼出来的两课

为四面体补饱和度阶梯时，第一版 sat_check 报"格点恒等最大偏差 0.37、全部
格点违例"——数学上不可能（四面体是角点凸组合，格点处权重全落单点）。两个
bug 都在检查器自己身上：

1. **恒等语义写反**：`apply(格点存值)` 是把 LUT 的**输出**当输入喂回去。
   正确语义是"输入取格点**坐标** (i/(n-1))，输出与该格点**表项**逐位相等"
   ——只有 identity LUT 才有 apply(表项值)==表项值。
2. **归一化漏乘 scale**：每细步跨的格胞数是 maxM/M，我写成
   maxM/(scale·M)，虚增 64 倍，把 0.03 的正常变化报成 1.9 的"振荡"。

修正后四张 adapted 产物：格点恒等 65³ 全点零偏差；6 个面对角饱和阶梯的
细步每格胞变化与源数据自身跳变一致（如 Velvia 0.030-0.060 vs 源
0.029-0.054），无插值振荡。**冒出"数学上不可能的巨大违规"时，先怀疑检查器
的语义和量纲，再怀疑被检代码**——与第 14 条（检查器越界）同族，但这次
连"量纲要过一遍手算"都要写进习惯。

### 17. "官方机型没覆盖"是真实用户的日常——三家 RAW 一跑就现形

用户提供尼康/松下/奥巴三家 RAW 后立刻抓出两个缺口：测试写死 PHOTO 合约
（第三方 LUT 全被拒），温度白平衡对 LibRaw adobe_coeff 表没有的机型
（OM-5、Panasonic S9——cam_xyz 全零）直接报错。此前全套件只用索尼样片，
"全绿"的隐含前提是"索尼系文件"。**测试资产与样片库的覆盖面本身就是功能
边界**——新样片家族进来的第一件事是全套件重跑，失败项里一半是产品缺口，
另一半是测试自身的写死假设（两者都要修，且都要分辨清楚）。

配套教训：查失败点写直捣最底层的探针（RAWProcessor::process 拿错误码），
不要隔着 FFI 层猜。本次我猜了两次白平衡矩阵/迭代都不是真失败点，
探针 10 分钟定位。

### 18. "预览正常、点开异常" = 元数据路 vs 像素路的分叉

松下 S9 的 RW2 在 app 里缩略图正常、全图渲染白底紫点。缩略图走内嵌
JPEG（相机生成，永远正常），全图走 LibRaw 像素解码——两条路在"预览正常"
时也会分叉。宿主 CLI 渲染同一文件完全复现，排除了 app 层；根因是 LibRaw
0.21.5 对 DC-S9 压缩流不支持（元数据表认得出机型、像素解压错位），且
pre_mul 全 1 连相机白平衡都是坏的。DC-S9 需要 LibRaw 202502 snapshot / 0.22。

**两条通用教训**：①"预览好、全图坏"直接查解码库版本与新机型支持矩阵，
不要在 app 管线里找；②LibRaw 元数据能认出机型 ≠ 像素流能解——判断支持
与否必须渲染出图看，Changelog/support 列表是唯一可信来源。
